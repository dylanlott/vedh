<objective>
Make card resolution both fast and deliberate: add the indexes the lookup has always needed, add the
distinct-name projection the suggestion ranking will use, and turn today's arbitrary choice of
printing into the documented `(name, set code, collector number)` disambiguation of D-09 with a
warning when the requested printing is not in the snapshot.

Purpose: the `cards` table has no index on the name or face-name columns today — only a primary key
on the identifier and a unique index on the row identifier — so every deck import sequentially scans
roughly ninety-seven thousand rows. That is a prerequisite for the sub-minute time-to-board target,
not an optimization. And because the current lookup keys its result map by name while the table holds
one row per printing, which printing a player gets is decided by row arrival order. D-09 makes that
choice explicit; D-10 keeps a stale snapshot from silently shrinking a deck whenever a new set ships.

Output: one migration set across both migration directories, a refresh hook on the snapshot import
path, an index-usable batch lookup, and printing-aware resolution inside `previewDeck`.
</objective>

Create table `card_names` with `name_lower TEXT PRIMARY KEY` and `display TEXT NOT NULL`, guarded by
`IF NOT EXISTS`. Populate it from `cards` by selecting distinct lower-cased values across a union of
the name column and the face-name column, excluding null and empty values, keyed by the lower-cased
form with `ON CONFLICT DO NOTHING`. A projection over distinct names rather than the printings table
itself is the point: the table holds roughly ninety-seven thousand printings against roughly
thirty-three thousand distinct names, so indexing printings would produce a three-times larger index
and a result set whose top three rows are frequently three printings of the same card — useless as
three suggestions.

Create `card_names_trgm_gist` on `card_names` using GIST over the lower-cased name with
`gist_trgm_ops`. GiST rather than GIN is decided by correctness, not by benchmarking: the GIN
trigram operator class accelerates only the boolean similarity operator, which returns zero rows for
a needle below the similarity threshold — and D-03 requires the nearest matches to be shown even
below the cutoff. The GiST distance operator answers that in one index-ordered scan, unconditionally.

Create `cards_name_lower_idx` on the lower-cased name, `cards_facename_lower_idx` on the lower-cased
face name, and `cards_name_set_num_idx` on the lower-cased name plus set code plus collector number,
all with `IF NOT EXISTS`. An expression index on a lower-cased column only helps a query that also
lower-cases, which is why task 2 changes the query text as well.

**Widen the existing batch lookup.** In `server/cards.go`, add the set-code, collector-number and
Scryfall-identifier columns to the SELECT list and scan each into a nullable string local mapped
through the existing pointer helper, exactly like every other optional column in that function.
Populate the four D-07 fields on the returned `Card` where the data exists; leave them as empty
strings otherwise, and treat an empty value as "unknown printing" rather than as an error, because
game payloads written before this phase have no such keys and unmarshal them as empty.

Change the WHERE clause to compare the lower-cased column against a lower-cased parameter array on
both the name and face-name columns, and lower-case the needles in Go before binding them. The
function already lower-cases for map keying, so this is strictly wider than today's case-sensitive
comparison and no existing caller loses a match — state that in a comment, and prove it with a test
asserting a lower-cased needle matches a mixed-case stored name. An expression index over a
lower-cased column is unusable by a query that does not lower-case, so changing the query text is
the half of Pitfall 1 that is easy to omit.

Keep `s.db.Query` versus `QueryContext` consistent with the surrounding function's existing style
here; the context-aware form is required in `server/deck_import.go`, which plan 01-01 already
established, and this task does not need to churn the public `cards` resolver's signature.

**Add printing-aware resolution.** In `server/deck_import.go`, replace the name-only resolution step
with a two-stage resolve.

Stage one, exact printing: for every parsed entry that supplies a set code or a collector number,
issue one batched query keyed on the lower-cased name, the lower-cased set code, and the collector
number, using the ordinality-preserving unnest-over-parallel-arrays form so results map back to
entries without a second lookup. Bind every value as a parameter; never compose SQL with string
formatting, including for any limit. Set-code comparison lower-cases both sides so the upper-case and
lower-case spellings of one set select the same row — the corpus in plan 01-02 asserts the parser
preserves the spelling verbatim, and normalizing at query time rather than at parse time is what
keeps the parsed value available for the future reconciliation D-10 anticipates.

Stage two, name fallback: every entry not matched in stage one — including an entry whose set code
simply is not in this snapshot — resolves by lower-cased name alone. When an entry supplied a set
code and stage one missed but stage two hit, attach a warning in player-facing language naming the
requested set code and stating that a different printing was used, keep the parsed set code on the
entry so a later snapshot refresh can reconcile it, and do **not** report the entry as unresolved. A
stale snapshot must not silently shrink a deck every time a new set ships.

Make the name-only choice deterministic. Today which printing wins is decided by row arrival order,
which is arbitrary. Order the fallback query by a documented, stable key — lower-cased set code then
collector number then row identifier — and record that ordering in a comment on the query, so the
printing a player gets is a decision rather than an accident.

Preserve every behaviour of the analog in `server/cards.go`: dedupe needles by lower-cased name
before querying, tolerate a missing relation with the existing helper so a server running ahead of
its migrations degrades instead of failing, and accumulate per-row scan errors with the existing
multi-error combiner rather than aborting the whole preview.

Introduce the low-confidence cutoff as a Go constant applied to a returned score, with a doc comment
stating that a score exactly equal to the cutoff counts as confident and that the cutoff appears
nowhere in SQL — which is what makes it tunable without a migration or a contract change. Plan 01-05
consumes it; declare it here alongside the resolution code it belongs to.
