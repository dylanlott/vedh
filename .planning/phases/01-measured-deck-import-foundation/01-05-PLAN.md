<objective>
Close the two halves of REQ-ACT-002 that the preview screen's trustworthiness rests on: give every
unresolved card up to three ranked candidates in the same round trip, with the worst-case cost bounded
to a constant; and make the created library come from the same parsed, resolved deck the preview
reported, so the number a player is shown is the number they get.

Purpose: today a single bad row fails the entire deck, and there is no warning or partial model at
all. This plan is where the warnings, blocking errors, and continue-anyway triad becomes real, and
where the ordering defect that would otherwise reject a hundred-and-one-card paste containing two
unmatched names gets fixed — because the size check currently runs before lookup, and D-05 requires
the count to exclude what could not be matched.

Output: bounded eager suggestions with their own instrumentation, and a `createLibraryFromDecklist`
that cannot parse anything.
</objective>

Declare three constants with doc comments naming what each bounds: the maximum number of distinct
needles at 25, the sub-budget at 750 milliseconds, and the candidates per entry at 3.

Build the needle set from unresolved entries only, de-duplicated by lower-cased name using the same
block `server/cards.go` already uses for the exact lookup. This first bound is the one that matters
most and it inverts the intuition that a hundred-card deck means a hundred lookups: the ninety-eight

is not the normal case scaled up — it is a distinct pathological case, a garbage paste or a snapshot
that failed to load. If the de-duplicated set exceeds the maximum, keep the first 25 in input order,
append one warning naming both the shown count and the total, and increment the truncation counter.

Issue one query for the whole needle set: an ordinality-preserving unnest over the needle array,
cross-joined laterally against a subselect that orders `card_names` by the trigram distance operator
against the needle and limits to the candidate count. Order the outer result by the needle ordinality,
then by score descending, then by the displayed name ascending — the last key is what makes two
equal-scoring candidates have a specified, stable order rather than whichever the planner emitted.
Bind both the needle array and the candidate limit as parameters; compose no part of this SQL with
string formatting.

Run the query under a sub-context derived from the request context with the sub-budget as its
timeout. On any error, including a deadline exceeded, log through the request-scoped logger, return
zero suggestions plus one player-facing warning stating that suggestions are temporarily unavailable,
and let the preview succeed with its `CanContinue` value unchanged. That is D-01's never-block-the-
player rule applied to the suggestion path itself.

Map each candidate onto the `DeckSuggestion` shape declared in plan 01-01, computing
`LowConfidence` in Go from the cutoff constant plan 01-04 declared — a score exactly equal to the
cutoff is confident. When nothing clears the cutoff, return the nearest candidates anyway, all marked
low-confidence, rather than an empty list. This is why the projection is indexed with the GiST
trigram operator class: the boolean similarity operator returns zero rows below the threshold, so it
structurally cannot serve this case, whereas the distance operator returns the three nearest
unconditionally and turns the cutoff into a presentation concern that is cheap to retune.

Attach candidates only to the `Unresolved` issues. Do not add, and do not later be tempted to add, any
field on an entry that could hold a corrected name — the API shape is the guarantee that the server
never rewrites what a player typed, and a player accepting a candidate is an explicit action that
lands in Phase 2's correction UI.
