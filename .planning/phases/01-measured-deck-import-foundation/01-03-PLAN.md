<objective>
Add the browser half of the activation funnel: one persisted random session identifier per browser,
and a fire-and-forget `track()` that sends one mutation per event with only allowlisted campaign
attribution attached.

Purpose: the client is the only place that knows when a view happened or when a board became
usable, and the sharpness of those timestamps *is* the time-to-board metric. This service is also
the boundary where an accidental leak would be easiest — a decklist, a deck URL, or a full
referring URL — so its allowlist and its storage discipline are the substance of the work, not
decoration around it.

Output: `app/src/services/productEvents.ts`, its mutation document, and a vitest suite in the only
directory this project's vitest configuration actually collects. No Vue component and no store:
`ui.plan-gate` returned `frontend: false` for this phase, and every activation UI is ACT-004 in
Phase 2.
</objective>

`track(name: string, metadata: Record<string, string | number> = {}): void` sends exactly one
mutation per call, does not await, and attaches a catch handler that logs at debug level with the

time-to-board metrics. It converts the metadata record into the key/value pair list the input
expects, stringifying numeric values. It never reads the auth storage key and never places an
authorization value into metadata; the server attaches the authenticated user identifier itself from
the request context and ignores any identifier in the payload.

Add a file-header comment recording that the client-side allowlist implemented in task 2 is a
convenience, not a control: the server-side per-event key allowlist in `pkg/telemetry` is the
enforcement point, because the client is not a trust boundary.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| page URL and referrer → client event service | Attacker-choosable query-string and referrer values enter here |
| client event service → GraphQL API | Everything this service sends is untrusted by the server; the server's own allowlist is the control |
| browser storage → client event service | A stored value may be absent, empty, corrupted, or unreadable |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-17 | Information Disclosure | `captureAttribution` | high | mitigate | Frozen key allowlist, referrer reduced to its host so no path or query string can be emitted, 128-byte truncation; the server-side per-event allowlist in `pkg/telemetry` is the enforcing control |
| T-01-18 | Information Disclosure | `track` metadata | high | mitigate | The service never reads the auth storage key and never places an authorization value into metadata; the server attaches the authenticated user identifier from the request context and ignores any identifier in the payload |
| T-01-19 | Denial of Service | `track` | low | accept | One mutation per event is deliberate (D-19) and unbatched; a client can already issue arbitrary GraphQL requests, so this adds no new capability. The per-surface rate limit in plan 01-06 bounds the server side |
| T-01-20 | Tampering | session identifier | low | accept | The identifier is a non-identifying analytics value, client-readable by design, and is accepted by the server only as `product_events.session_id`. It is never an authorization input, which plan 01-01's threat register covers as T-01-12 |
| T-01-06b | Spoofing | client-submitted event names | medium | transfer | Enforcement belongs to the server: `pkg/telemetry.ValidateEvent` rejects any name outside the closed 15 and any client submission of a server-owned event. This client makes no attempt to enforce it |
