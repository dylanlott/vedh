# Plan 01-10 — Close REQ-ACT-003 traceability honestly

<objective>
Plans 01-08 and 01-09 delivered the Archidekt adapter and pinned its contract. This plan makes
the tracking artifacts tell the truth about that — no more, no less.

This is deliberately the last wave, and deliberately contingent: traceability may only be
updated on the back of 01-09's passing tests. Marking a requirement complete because code was
written, rather than because behavior was proven, is the exact failure this ordering prevents.
</objective>

<context>

## Current state of the artifacts

- `COVERAGE.md` records all 6 provider capabilities as **OPT-OUT**, each justified by the
  unverified Moxfield contract. The `verify:pre` api-coverage gate currently reports
  `6 capabilities, 6 opt-out` and passes on that basis. Those reasons are now obsolete.
- `.planning/REQUIREMENTS.md` leaves **REQ-ACT-003 Pending**. That was the honest call while no
  working import existed. Whether it is still honest is this plan's central judgment.
- `docs/research/deck-provider-feasibility.md` has 01-08's revised Archidekt decision section.

## REQ-ACT-003's actual text — check each clause

> Public deck provider feasibility gate and first adapter — one-day time-boxed comparison of
> public Archidekt and Moxfield access; decision record; adapter interface keyed by an
> allowlisted hostname; HTTPS, DNS/IP validation, redirect revalidation, 3s connect / 8s total
> timeout, 1 MiB cap; normalize through ACT-002; server-side feature flag and kill switch.

Every clause has a specific owner: the comparison and decision record from 01-07 plus 01-08's
revision; the hostname-keyed interface and all the SSRF controls from 01-06; normalization
through ACT-002 and the flag/kill switch from 01-08 and 01-09.

Judge clause by clause against passing tests. If all clauses hold, mark it complete. If any does
not, leave it open and state precisely which clause and why — a half-true "Complete" is worse
than an accurate "Pending", because it silently removes the item from every downstream audit.

Note for context, not as a thumb on the scale: ROADMAP criterion 5 is explicitly either/or and
was already satisfied by the decision record alone. This plan is about REQ-ACT-003's own
narrower promise.

## The one thing that is genuinely not done

Nobody has read `https://archidekt.com/terms`. The page is JS-rendered and no agent in this phase
could read it. `robots.txt` permits the `/api/decks/` path, but robots.txt is not a licence.

This does **not** block the adapter existing — the kill switch defaults off, so a default
deployment makes no outbound Archidekt request. It **does** gate enabling. Record it as an
operator precondition, not as a code gap, and put it where whoever sets
`DECK_PROVIDER_ENABLED=true` will actually encounter it.

</context>
