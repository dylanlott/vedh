<decisions>
Decisions this plan makes and records (Claude's Discretion items flagged in 02-CONTEXT.md):

- **DEC-A — `GUEST_CREATION_ENABLED` defaults to `true`.** Phase 1's `DECK_PROVIDER_ENABLED`
  defaults `false` because it dials a third party (SSRF surface, unread terms of service).
  Guest creation dials nobody: it is an internal, rate-limited, bcrypt-backed write on our own
  table. Shipping it `false` would make this entire phase inert on merge and would leave Phase 5's
  release gate unable to exercise the guest journey without an out-of-band flag flip. The switch
  exists so an operator can *kill* the funnel under abuse, not so the funnel starts dead.
- **DEC-B — guests are created with `expires_at = NULL`.** This is the single assignment that
  makes D-2.1, D-2.2 and D-2.3 coherent: the row lives indefinitely (D-2.1), `expires_at` stays on
  the schema and stays enforced when minting a *new* token (D-2.2), and no visitor ever meets an
  expired-session wall (D-2.3). A non-null `expires_at` is an explicit operator mark meaning
  "this guest is marked for removal" — the only rows the cleanup path in plan 02-02 will ever see.
- **DEC-C — one rate-limit `Registry`, one new `Surface`.** `SurfaceGuestSession` joins the
  existing `s.limiter`; no second `Registry` is constructed (it would fragment idle eviction and
  the `vedh_rate_limit_total` mental model).
- **DEC-D — the guest re-auth credential is a separate secret with its own storage key.** Minted
  with `crypto/rand`, returned once from `guestSession`, stored server-side only as a hash in the
  new `guest_credential_hash` column, and persisted client-side under `edhgo/guest-credential` —
  never inside the `edhgo/auth` profile, never reusing the analytics session identifier (D-2.4).
</decisions>

<assumption_delta_decision>
**Detector fired** (`pluralization` / `optional` / `chosen`). The core assumption that lost its
monopoly: a vEDH user had exactly one name — `username`, required and `UNIQUE` — used for both
identity and display. This phase introduces a second, optional, non-unique name.

- **Primary noun (rendering):** *display name*, resolved through the single expression
  `display_name ?? username`. This is a **promote**: "the name a person is shown as" becomes the
  primary rendering concept, and `username` is demoted to one variant of it (the fallback for
  people who typed nothing).
- **Primary noun (identity):** `username` is unchanged and remains the unique system identity and
  the join key. This is deliberately *not* generalized — `BoardView.vue` joins `game.Players` to
  `auth.profile` on `Username` in dozens of places, and D-2.6's "globally unique across all users"
  is what keeps that pre-existing logic correct.
- **Decision:** `promote` for rendering, `no-change` for identity. The two nouns are separated, not
  stacked.
- **Invariant that must not regress:** every *display* site resolves through the fallback and every
  *identity* site compares on `Username`; no site does both. Plan 02-05 carries the sweep and the
  test that encodes this, and this plan's `guestSession` is what makes the identity half safe by
  generating names into the same unique namespace rather than beside it.
</assumption_delta_decision>

**Guest credential format (DEC-D, load-bearing for plan 02-02's O(1) lookup).** The credential
returned to the client is the row's `uuid`, a single `.` separator, and a 32-byte `crypto/rand`
secret encoded base64url without padding. Only the secret half is hashed through `hashPassword`
into `guest_credential_hash`; the uuid half is the lookup key so the re-auth path can find exactly
one row and bcrypt-compare once, instead of scanning every guest. The credential is never rotated on
re-issue, so two tabs of the same browser continue to hold a working credential.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| anonymous browser -> `guestSession` mutation | Wholly untrusted, unauthenticated input on a public write path that creates a database row |
| anonymous browser -> `previewDeck` mutation | Already-hardened Phase 1 boundary; reached for the first time from a public route in this plan |
| guest JWT -> every existing authenticated resolver | A guest token now satisfies `requireAuth` exactly as a real user's token does |
| server -> browser (guest credential) | A high-entropy bearer secret crosses the wire once, at creation |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-01 | Denial of Service | `GuestSession` resolver | high | mitigate | `allowRequest(ctx, ratelimit.SurfaceGuestSession, clientKeyFor(ctx, sessionID))` runs before any DB write; `clientKeyFor` is address-anchored so rotating `sessionID` cannot mint fresh buckets. Proven by `TestGuestUsers_RateLimit`. |
| T-02-02 | Denial of Service | guest-creation feature surface | medium | mitigate | `GUEST_CREATION_ENABLED` kill switch checked before the rate limiter and before any write; proven by `TestGuestUsers_KillSwitch`. Default is `true` (DEC-A) — the switch is an operator kill, not a rollout gate. |
| T-02-03 | Spoofing | guest re-auth credential | high | mitigate | Credential is generated with `crypto/rand`, returned exactly once, and stored server-side only as a bcrypt hash in `guest_credential_hash`; client stores it under its own key and never attaches it as an `Authorization` header. |
| T-02-04 | Tampering | generated guest username vs. real usernames | high | mitigate | Uniqueness is enforced by the pre-existing `username_unique` database constraint with Go-side retry on `23505`, not by an application pre-check (which would race under concurrent creation). | T-02-05 | Information Disclosure | guest password column | medium | mitigate | The guest's password is `crypto/rand` and hashed through the existing `hashPassword` at bcrypt cost 14 — identical treatment to a real user's, never a cheaper hash for a "throwaway" account. |
| T-02-06 | Tampering | `display_name` free-form user input | medium | mitigate | Rendered exclusively through Vue `{{ }}` interpolation (auto-escaping, never `v-html`) and length-bounded by the `VARCHAR(255)` column plus a client `maxlength`.
